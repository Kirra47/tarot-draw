# 星象塔罗：轻量化体验改进计划书

版本：v1.0 · 2026-09-24  
阶段：产品与实施方案，尚未修改网站或发布  
适用对象：个人日常使用、朋友体验、线下项目演示  
主要设备：安卓手机；兼顾桌面与平板

## 1. 本次改进要解决什么

让用户写下问题、完成一次抽牌或起卦，就能很快读到与问题有关的简短解读。愿意深入研究的人，再自行展开依据和详细资料。

用户已经明确表达的问题包括：开始前要选太多东西；结果页要读很长；多个体系相互交叉；术语和说明文字过多；重要的 AI 解读不够突出。

本次以三个结果衡量改进：

1. 少操作：常用流程不必重复选择牌阵、起卦规则和资料层。
2. 少阅读：先看到直接回应、两条重点和一个下一步。
3. 不丢上下文：追问、展开和重试都围绕同一次结果进行。

保留已经投入开发的抽牌、捏合手势、确定性起卦、传统资料、AI、记录和分享能力。调整它们的出现时机、默认状态与信息层级。

参考《天机六爻》的目标是借鉴用户希望获得的轻巧体验。本计划没有完成该游戏的完整交互实测，不声称复刻其界面、排盘算法或内部实现。

## 2. 现状核查与问题定位

以下事实来自本机 `D:/codex/tarot-draw` 源码静态检查。没有在本次工作中调用付费 AI、做性能跑分或验证线上部署状态。

| Before：当前实现 | After：本次方案 | Why：用户收益 |
| --- | --- | --- |
| 初始 `readingMode='combo'`，新一轮又重置为二合一 | 首次访问建议默认起卦，之后记住用户上次选择 | 直接开始，减少重复选择 |
| `traditionalLayer` 首项为梅花＋奇门＋八宅，重置也恢复全部 | 日常默认仅使用所选主体体系；奇门、八宅放入可选的进一步分析 | 与当前问题无关的资料不再占主流程 |
| 起卦下拉框同时包含时间、三个数字、射覆、失物等不同概念 | 内部分开“怎么起卦”和“问的是什么”，页面只展示必要输入 | 数字起卦与射覆可以同时成立 |
| 结果 DOM 顺序是本卦资料、传统资料、AI 分析、牌面参照 | 紧凑卦象/牌面摘要之后，立即展示 AI 短解 | 更快找到真正想看的内容 |
| 系统提示词要求本卦、逐牌、关联及传统资料等多个章节 | 首次只生成短解；详细分析按需请求 | 从生成源头减少字数与等待 |
| 初次 AI 请求结束后，存在自动请求奇门解释的逻辑 | 奇门解释仅在用户主动打开并请求时生成 | 默认一次解读只发一个 AI 请求 |
| 主解读失败时会用错误块替换整个内容；追问失败时也会换成本地回复 | 保留已收到的文字，标注“未完成”；重试绑定原会话 | 解决“刚输出又消失”的风险 |
| 部分结构已经折叠，但主结果前仍有多个大型内容区 | 统一为短解、详细解释、原始依据三个层级 | 减少层层重复和阅读顺序混乱 |
| 移动端 Hero 当前有约 400px 的固定高度设计 | 手机首页使用紧凑品牌区，把输入和按钮放进首屏 | 打开后更快开始操作 |

现有代码有两份明显不同的站点目录：`tarot-draw` 包含近期功能，`tarot-site/public/tarot.html` 是较早副本。实施以 `tarot-draw` 为候选基线；发布前必须核对真实部署来源，避免覆盖成旧版。

## 3. 产品范围与建议默认值

### 3.1 三种模式继续保留

首页保留一排紧凑选择：**起卦 / 塔罗 / 二合一**。不再用三张大卡片、长副标题和多段解释占据屏幕。

| 模式 | 默认行为 | 首屏结果 | 可展开内容 |
| --- | --- | --- | --- |
| 起卦 | 按当前起卦规则生成一次卦；明确给数字时优先处理数字 | 本卦小图、卦名、AI 短解 | 动爻、变卦、互卦、体用、原典与取数过程 |
| 塔罗 | 默认三张；提供快速抽取和亲手抽牌 | 三张牌的紧凑预览、AI 短解 | 逐牌含义、正逆位、牌阵关系 |
| 二合一 | 一次操作锁定牌面和卦象 | 一份综合短解，附紧凑牌面与本卦 | 两者分别解释、共同点与差异 |

首次默认“起卦”是本计划建议，依据是用户目前希望参考六爻类体验、减少抽取步骤；这是待实施的产品选择，并非已经改变的网站行为。老用户若已有保存的偏好，应优先沿用。

### 3.2 默认配置

| 项目 | 建议值 |
| --- | --- |
| 阅读长度 | 简短；首页不增加“长度设置” |
| 塔罗牌阵 | 三张；五张收进“更多设置” |
| 起卦方式 | 按时间；明确指定数字时使用数字 |
| 奇门、八宅 | 默认不附加到日常解读；需要时主动选择 |
| 抽取方式 | 快速抽取优先；亲手抽牌作为保留入口 |
| 摄像头 | 不自动开启；用户启用手势后才申请 |
| 摄像头画面 | 继续隐藏，保留手势识别和退出入口 |
| 展开状态 | 每次新结果先展示短解；同一结果内记住展开和滚动位置 |
| 记录 | 自动保存本次结果；历史入口放右上角 |

只记住稳定偏好，例如模式、三/五张、快速/亲手抽取、文字大小。每次问题、三个数字、现场描述、房屋朝向属于本次输入，不自动带进下次。手势偏好不能绕过每次设备授权，也不能导致一开页面就启动摄像头。

### 3.3 本轮不扩展的内容

不把账号、支付、咖啡馆订单验证、商业后台、模型微调和新术数引擎混入这轮改进。它们不会直接解决“太繁琐、看太多”的核心问题。

当前项目的起卦核心是梅花易数。展示六条爻线，并不等于已经实现完整六爻纳甲、世应、六亲和用神体系。界面继续准确标明起卦方法；如以后新增完整六爻功能，应另列功能与规则验收。

## 4. 新的主流程

```text
写问题 / 沿用当前模式
          ↓
点击“起一卦”或“开始抽牌”
          ↓
锁定本次数字、时刻、卦象 / 牌面
          ↓
紧凑结果 + AI 短解
          ├─ 继续问：沿用本次结果
          ├─ 看详细分析：按需补充解释
          ├─ 看依据：本地资料直接展开
          └─ 新问题：创建新的一次
```

普通起卦只需要填问题和点击主按钮。塔罗快速模式由一次点击完成三张抽取并进入解读；喜欢亲手抽牌的用户可以保留现在的操作方式。

“快速”只压缩点击与展示步骤，不改变牌库规则、正逆位规则和去重规则。结果在本次抽取时一次确定，动画结束、刷新展示、查看详情和重试 AI 都不能改变结果。

二合一保持原有约定：亲手抽牌时，以第一张牌确认时刻锁定时间卦；快速抽取时，在首张牌被确定的同一动作中锁定。使用用户给出的三个数字时，时间仅作为记录元数据，不得覆盖数字起卦。

## 5. 首页信息结构

### 5.1 默认可见内容

手机首页只保留品牌/历史入口、一行简短标题、问题输入、三模式切换、一个主按钮，以及弱化的“更多设置”。

```text
星象塔罗                         历史

你想问什么？
┌────────────────────────────┐
│ 例如：周末要不要去那场活动？ │
└────────────────────────────┘

       起卦   塔罗   二合一

按时间起卦 · 可改用三个数字

           [ 起一卦 ]

更多设置
```

不要求用户先选择“感情、工作、财运”等类别。问题类型由文字初步识别，只用于组织回答；确实影响计算且信息不足时才追问。

问题可以留空，保留“随便看看”的能力。空问题对应一般性解读，不编造某段关系或某个事件，也不额外弹确认框。

### 5.2 更多设置

仅展示当前模式有关的选项。塔罗模式显示三/五张、快速/亲手抽牌；起卦模式显示时间/数字及其他输入方式；二合一组合相关设置。奇门和八宅放到“附加分析”。

八宅只有在用户主动启用时才显示朝向输入。射覆、失物等不再与时间、数字混在一个下拉框里；自动识别后可用一条可修改的小标签表示。

首屏保留当前方式的简短说明，例如“数字起卦 · 5 / 7 / 8”，让自动化过程可核对。不得为了界面简洁把实际使用的规则完全藏起来。

### 5.3 按钮和错误反馈

主按钮使用具体动词：“起一卦”“开始抽牌”“开始”。点击立即反馈，提交期间防止重复创建会话。

缺少数字等输入错误显示在相关字段旁，并定位到可修正的位置。按钮不能无解释地灰掉。返回首页应保留草稿；只有主动新建一次时才清理本次输入。

## 6. 数字起卦与问题类型的规则

这部分是既有需求的硬约束，需要在简化界面时完整保留。

内部状态应分开保存：

- `readingMode`：起卦、塔罗、二合一。
- `castMethod`：时间、三个数字，以及已有的其他取数规则。
- `questionType`：一般问题、选择、射覆、失物等回答组织方式。

“用 5、7、8 起卦，看看我手里有什么”同时具有 `castMethod=three` 和 `questionType=shooting`。得到数字不能使射覆要求丢失；识别出射覆也不能把数字覆盖成时间。

输入优先与校验约定：

1. 用户在专用输入框明确填写的数字，或在问题里明确表达“用这三个数字起卦”，都属于显式输入。
2. 两处显式数字一致时直接使用；冲突时仅提示一次，供用户选择一组，不能暗中选一组。
3. 缺少数字、数字不合法或多于三项时就地说明；不得静默改按时间起卦。
4. 日期、年龄、价格和普通数量不能仅因含三个数字就被自动认作数字起卦。
5. 支持全角数字及常见分隔符；“三个数字 5.7.8”在语义明确时按三个整数处理；小数和含糊输入需要确认。
6. 用户明确选择单塔罗时，不擅自改成二合一；如果问题中又要求数字起卦，提示可切换模式。
7. 起卦时间与时区、原始数字、规则版本随结果保存。展开依据、追问与 AI 重试必须使用同一份快照。

## 7. 结果页：先短解，再展开

### 7.1 第一层：默认展示

顺序固定为：当前问题、紧凑卦象/牌面、AI 直接回应、最多两条重点、一个下一步、追问入口。

建议初次短解总量为 **120—180 个中文字，软上限 220 字**。简单问题允许更短；不能为凑字数补套话，也不能在句子中途硬截断。

| 内容 | 建议长度 | 作用 |
| --- | --- | --- |
| 直接回应 | 20—45 字 | 先回应用户正在问的事 |
| 重点 | 最多两条，每条 20—40 字 | 说明关键影响或需要留意的变化 |
| 下一步 | 15—35 字 | 给出一个可以执行或核实的动作 |

使用普通中文小标题，例如“这次怎么看”“留意这两点”“可以先做”。避免同时出现“观照、观测、洞察、能量、指引、启示”等近义词层层包装。

```text
周末要不要去那场活动？
[本卦小图 / 三张牌缩略图]   [名称]

这次怎么看
一段直接回应问题的短解。

留意这两点
· 与问题直接有关的一点。
· 另一个关键条件或变化。

可以先做
一个具体动作。

[继续问……                    发送]

看详细分析       看卦象 / 牌面依据
```

紧凑卦象/牌面仍然保留仪式识别感，但不在短解之前展示大盘、逐牌长文或整块传统资料。

### 7.2 第二层：详细分析

用户点击“看详细分析”后，按当前体系补充 350—600 字左右的说明。起卦重点解释本卦、相关动爻与变化；塔罗解释各牌与问题的联系；二合一说明相通或不一致之处。

详细分析继承已经展示的短解和同一份牌/卦数据。不能一展开就换一套相反答案；出现信息不足或不同解读时应具体说明原因。详细生成不会覆盖初次短解。

默认只生成一次，折叠后重新展开使用已保存内容，不重复调用 API。过长章节优先删重复内容；软长度目标失败时保留完整句子，并允许用户折叠。

### 7.3 第三层：原始依据与其他体系

动爻、互卦、体用、卦辞、爻辞、牌义、起卦记录放入“看依据”。本地已有数据直接显示，无需等待 AI。

奇门、八宅等附加内容在用户选择之后出现。奇门先展示一句简短主题和“用白话解释”，九宫盘进一步展开；八宅缺朝向时只在这个区域提示补充，不阻断其他流程。

来源说明集中放在对应依据面板。明确区分原典、本站说明、AI 解读与本地基础说明。把必要提示集中写清楚，避免每个段落都重复同一句免责声明。

## 8. AI 解读改造

### 8.1 按请求目的组织输出

将现有“大报告”提示词拆成用途不同的请求模板：`brief`（短解）、`detail`（详解）、`followup`（追问）、`qimen`（按需奇门解释）。模板共享同一份会话资料和措辞规则。

首次默认只发一个 `brief` 请求。不能先生成整篇报告，再只显示前几行；那样等待、成本和重复输出都没有真正减少。

短解只带当前体系和当前问题需要的资料；未启用的奇门/八宅不传入，也不让模型为其生成章节。详细分析按请求主题增补依据。

本轮沿用可配置的模型入口，不把换模型当成界面简化的前提。字数目标、token 上限和超时值均配置化，以真实输出验证，不能把 token 数当作中文字数。

### 8.2 回答内容要求

- 第一段直接回应问题，不从“这组牌呈现出……”开始长篇铺垫。
- 一次只强调最相关的两点；不把所有牌义、卦义逐项抄进短解。
- 如果有术语，紧跟一句白话；不要求用户先读术语表。
- 用户没有提供的身份、经历、现场信息和第三方想法，不当作已知事实。
- 不输出隐藏思考过程；只给面向用户的简短解释和可查依据。
- 不用凭空生成的“准确率、吉凶分数、成功概率”营造精确感。
- 数字、卦名、爻位和牌面以程序结果为准，AI 负责解释。

### 8.3 根据问题调整形式

| 问题类型 | 短解应优先回答 | 避免的输出 |
| --- | --- | --- |
| 去不去、做不做、二选一 | 条件下的倾向、关键取舍、下一步核实 | 只说“顺其自然”，或把象征解读写成必然结果 |
| 关系与沟通 | 互动角度、可观察信号、一个沟通动作 | 断言对方真实思想与隐私 |
| 工作与近期安排 | 当前重点、阻碍、一个近期动作 | 罗列所有可能性而不回应当前问题 |
| 射覆 | 颜色、形状、材质/触感、2—3 个候选 | 只给抽象寓意，或声称真的看见了物品 |
| 失物 | 有顺序的排查位置与可核对线索 | 伪造精确位置或肯定找得到 |
| 留空随看 | 一段明确标为一般性观察的短解 | 编造用户正在经历的事件 |

射覆默认可以用三行属性和两三个候选替代一般问题的“两条重点”，控制在同一阅读预算内。问题类型决定呈现方式，不自动换卦。

### 8.4 文案口吻示例

以下仅为语气示例，不对应真实牌阵或卦象：

冗长写法：“这次观照提示你关注外部机遇与内在阻力之间的张力，在能量流动中寻找属于自己的节奏。”

期望写法：“如果只是担心场面陌生，可以去看看，先给自己留好退路。出发前确认活动安排，并决定什么时候离开。”

文案应具体、自然、有条件，少用形容词；也不能把每个问题都回答成同一个“先行动、再观察”模板。

## 9. 输出稳定性和异常处理

静态代码已发现：`requestAIReading()` 的异常分支会替换已输出内容；`requestFollowUp()` 的异常分支会替换为本地回答。它们能够解释“文字出现后消失”的机制，但本次没有复现用户当时的网络错误，不能据此断定唯一故障原因。

改造要求：

1. 首次收到内容后保留缓冲和渲染结果；流中断时显示“这次解读未完成”，保留已收到部分。
2. 完全没有输出时，展示简短本地说明和“重试 AI”；本地说明不能冒充 AI 已完成解读。
3. 每个会话有稳定 ID 和不可变的牌/卦快照。旧请求晚到时不能写进新问题页面。
4. 重试同一解读不会重新抽牌、起卦或覆盖初次时间。已经完成的旧答复在新版本完成前继续可读。
5. 不把不完整回答存为“已完成”；保存状态、更新时间和完成标记。
6. 追问失败保留用户文字和已有回答；重试不重复增加追问计数或重复追加同一条消息。
7. 网络状态、真实服务错误、空响应与上游限流分别识别。按已知错误给对应提示，不能把所有失败都称为“限流”。
8. 不根据已输出字数模拟“完成百分比”；使用真实状态，如“正在解读”“仍在生成”“未完成”。
9. 用户滚动看前文时不强制滚回底部；详情展开不把整个结果重新渲染一遍。
10. 每个请求只允许一个活跃提交；不无限自动重试。超时阈值在实施测试中确定并配置，清楚区分首次响应和流中断。

已在生成的内容属于当前版本的增量展示；未完成状态要可见。网络恢复可以继续让用户重试，不承诺上游一定支持断点续传。

## 10. 安卓优先的界面与动效

### 10.1 响应式布局

| 尺寸 | 布局方向 | 重点 |
| --- | --- | --- |
| 手机 `<768px` | 单列、单一页面滚动；紧凑品牌区 | 输入、模式和主按钮优先；结果前不放大 Hero |
| 平板 `768—1199px` | 按可用宽高选择紧凑双栏或单栏 | 避免为保留桌面构图而压窄表单 |
| 桌面 `≥1200px` | 保留固定左侧 Hero、右侧独立交互区 | 切模式、展开右侧内容不移动左侧标题和魔方 |

不能只按宽度缩放；短屏、横屏、浏览器地址栏变化和虚拟键盘展开都要覆盖。桌面使用可用视口高度并设置合理的溢出规则；手机避免外层弹窗和内层内容同时滚动。

手机正文建议 17—18px；辅助文字一般不低于 14px；主操作触摸区域建议至少 48px。允许系统放大字体，不通过整体缩放让页面“塞得下”。这些是本轮设计目标，不代表已完成无障碍认证。

### 10.2 魔方与仪式感

保留当前深色、半透明、真实分层拧动的魔方。桌面继续作为固定 Hero 氛围；手机压缩其占用高度，必要时作为小范围背景或静态一帧，不能把输入区挤出首屏。

本轮不再次改魔方结构和材质方向。性能不足、页面不可见或用户选择减少动态时，应降级/暂停背景动画。进入结果页后，阅读和输入优先。

### 10.3 抽牌和手势

快速抽牌展示一次紧凑的翻牌过程；亲手抽牌保留现有捏合动作和触摸路径。仍不增加握拳撤回。

手势仅在用户主动进入时加载相关资源。退出手势或离开页面应释放摄像头，权限失败仍可触摸抽牌。摄像头实时画面保持隐藏。

按钮按下立即反馈，普通面板切换建议 150—250ms；大面积装饰动画不阻塞开始或阅读。减少动态模式保留必要状态反馈，降低位移与连续背景运动。

## 11. 记录、分享和二次使用

历史列表优先显示“问题＋日期＋一句短解”。次数、元素分布、高频牌和正逆位统计收进“统计”，不占日常历史首屏。

一次结果保存：问题、模式、实际起卦方法、原始输入、锁定时间与时区、牌/卦快照、规则版本、短解、详细分析、追问、生成状态。老记录没有新字段时可正常查看，不伪造缺失内容。

点击历史先展示短解；详细分析保留在同一条记录下。记录保存失败时提示实际状态，不能仍显示“已保存”。

分享默认采用简短版本：问题是否显示由用户选择，附紧凑卦/牌和短解；完整报告放到进一步选项。分享与重新查看记录不触发新的 AI 请求。

继续沿用本机记录模式，本轮不新增账号或云同步。手机重装、浏览器数据清理等场景下仍保留现有导出能力。

## 12. 技术实施建议

### 12.1 渐进调整现有代码

现有原生 HTML/CSS/JavaScript、Three.js、本地起卦模块与服务端 AI 代理足以支持本轮。优先调整渲染顺序、状态组织和请求模板，不因简化界面而迁移整个框架。

| 位置 | 计划工作 |
| --- | --- |
| `tarot.html` 的问题区、`updateReadingModeUI()`、`resetSession()` | 简化首页；偏好记忆；按模式展示选项 |
| `explicitThreeNumbers()`、`inferCastMode()`、`collectCastRequest()` | 分离起卦方法和问题类型；修正显式数字优先与歧义处理 |
| `showSettlement()` 及结果 DOM | AI 短解前置；紧凑结果；统一详细分析与依据面板 |
| `requestAIReading()`、`requestFollowUp()`、`readAIStream()` | 内容保留、完成状态、请求隔离、防重复与重试 |
| `requestQimenAI()` 调用点 | 取消初次解读后的自动附加请求，改按需生成 |
| `netlify/functions/tarot-reading.mjs` | 按用途选择提示词；输入校验；响应状态与内容预算 |
| `scripts/local-server.mjs` | 继续调用共用 AI 处理器，验证本地与线上协议一致 |
| `emil-redesign.css` | 手机紧凑首页、大字、单滚动区；保持桌面左侧稳定 |
| `service-worker.js` | 更新缓存版本并处理新旧脚本兼容，避免改完仍读旧页面 |
| 历史保存与海报生成函数 | 支持短解字段、旧记录兼容、分享选择 |

### 12.2 AI 接口与状态结构

建议新增 `purpose` 和会话版本字段；服务端白名单校验模式和用途。初期可以延续文本流，不强依赖模型支持严格结构化输出。

UI 区块可在服务器/客户端适配层整理成短解、重点和行动。格式解析失败时，仍展示原始短文本，不能因此抹掉回答。若后续采用 JSON 或结构化事件，先做模型能力验证，并保留兼容处理。

每个请求绑定 `sessionId + snapshotVersion + purpose + requestId`。详细分析与追问同时进行时各自管理状态；旧请求取消或返回后，不可污染另一会话。

复用确定性的起卦、排盘与牌库逻辑。API Key 保持服务端读取。本次不涉及密钥迁移和付费账户设置。

### 12.3 候选版与回退

先提供本地候选入口进行体验比较，保留当前可用版本。候选版不得清空历史、覆盖用户配置或改变现有线上入口。

完成验收后同步前后端与 PWA 缓存版本，核对本地、Netlify/实际托管来源，记录发布版本。异常时恢复上一完整版本；前端、后端协议与缓存要一起回退。

## 13. 实施阶段与交付件

按可验证结果分阶段，不预先承诺固定工期。

| 阶段 | 工作内容 | 交付与验收点 |
| --- | --- | --- |
| 第一阶段：先让结果好读 | 短解模板；AI 前置；隐藏附加大块资料；取消自动奇门请求；保留流式部分内容 | 同一测试牌/卦的新旧结果对照；初次只发一个 AI 请求；模拟断流时文字不消失 |
| 第二阶段：让开始更简单 | 紧凑首页；默认和记忆；更多设置；数字与题型分离；快速抽牌入口 | 三模式都能直接走通；明确给数不被时间覆盖；射覆能同时使用三个数字 |
| 第三阶段：把深入阅读收好 | 按需详细分析；依据面板；追问状态；历史与分享 | 展开不重抽、不重复请求；旧记录可读；追問留在同一次结果 |
| 第四阶段：安卓与发布验收 | 手机构图与字号；键盘/横屏；摄像头释放；PWA 更新；本地与托管一致性 | 安卓真机完整流程记录、桌面稳定性截图、版本与回退说明 |

第一阶段就必须产生明显改善。不要等所有可选功能做完，才让用户看到简短结果页。

## 14. 验收标准与测试方法

以下是目标和验收方法，尚无本轮实测成绩。网站性能指标用于交互与可靠性，不表示占卜准确率。

### 14.1 操作与阅读

| 指标 | 目标 | 验证方法 |
| --- | --- | --- |
| 普通起卦操作 | 输入问题后一次主按钮点击进入结果，无额外强制确认 | 首次/再次访问各走一遍 |
| 默认塔罗快速模式 | 一次主按钮触发三张抽取，无需逐张确认 | 固定测试流程与网络记录 |
| 初次短解 | 常见问题 120—180 字，软上限 220 字；关键回应在第一段 | 覆盖 20 个一般/选择/射覆/失物等测试问题，逐条检查 |
| 手机首屏 | 390×844 CSS 像素、默认字号、收起键盘时首页能看到问题输入和主按钮；结果首屏能看到直接回应和主要重点 | 截图核对；360px 窄屏允许自然滚动，禁止通过缩小字体凑首屏 |
| 可读性 | 默认正文 17—18px；字体放大到 200% 时仍能完成核心流程 | 浏览器与安卓字体/缩放测试 |
| 左侧稳定 | 桌面切换模式、牌阵与右侧展开前后，Hero 标题与魔方布局位置不变 | 相同视口截图和元素边界对比 |
| 用户是否看懂 | 找 3—5 位未熟悉项目的体验者，在约 15 秒内说出短解的重点 | 记录成功人数和原话，不外推为统计结论 |

### 14.2 正确性与稳定性

| 场景 | 必须满足 |
| --- | --- |
| “用 5、7、8 起卦，看看手里是什么” | 按这三个数字计算，同时给射覆属性与候选；保存明确输入来源 |
| 输入日期、价格、年龄 | 不误触发三个数字起卦 |
| 指定数字不齐或冲突 | 就地可修正；不静默改成时间 |
| 单塔罗 | 不出现或编造卦象、奇门和八宅结果 |
| 单起卦 | 不要求抽塔罗，不出现虚构牌面 |
| 二合一 | 一份简短主解读；不默认重复两份长报告 |
| 展开、追问、重试 | 本卦、爻位、数字、牌面与锁定时刻保持一致 |
| AI 首包失败、半途断流、空响应、限流 | 状态准确；已有内容保留；手动重试可用 |
| 旧请求晚于新会话返回 | 不覆盖新会话 |
| 连点、双击、快速切换 | 不重复建会话和调用 AI |
| 没有 AI 或离线 | 可以完成本地抽牌/起卦；基础说明明确标识 |
| 手势拒绝授权、退出、离页 | 触摸仍可用；摄像头退出后释放；视频画面保持隐藏 |
| 旧记录与存储写入失败 | 老数据可读；失败有准确反馈，不清空数据 |
| PWA 新旧缓存 | 刷新更新后版本一致，旧记录不丢 |

### 14.3 性能测量

首次解读默认 **1 次 AI 请求**；没有主动操作时，奇门 AI 请求为 **0**。同一详情再次展开新增请求为 **0**。这是可直接在网络面板验证的目标。

记录点击到界面响应、点击到本地卦/牌显示、AI 首个可见字延迟、AI 完成耗时、失败数/总请求数。界面响应目标为 100ms 级；本地卦象呈现目标为 500ms 内，测试中剔除人为仪式动画等待并单独记录。

AI 延迟不写死“秒出”。使用同一设备、同一网络、同一模型和一组固定问题，对当前版和候选版分别测量至少 20 次，报告中位数、P95 和样本数。样本较小时明确统计波动，不把短期结果当作服务承诺。

性能证据记录设备、系统、浏览器、模型配置、网络和时间。真实 API 测试产生调用费用，批量测量放在实施验收阶段；计划书阶段不调用。

### 14.4 复用已有检查

实施时优先运行并按变更补充现有的 `verify-meihua.mjs`、`verify-meihua-modes.mjs`、`verify-traditional.mjs`、`verify-reading-function.mjs`、`verify-followup.cjs`、`verify-cast-modes-ui.cjs`、`verify-archive.cjs`、`verify-pwa.cjs`。固定 DOM 选择器随新界面更新，但核心计算断言保留。

新增必要的场景检查集中在：数字与题型并存、流中断保留、跨会话请求隔离、首次请求数、旧档案兼容。不要为每个样式常量单独写测试。

## 15. 第一版边界与最终交付清单

第一版必须交付：紧凑首页、三模式保留、数字优先规则、短解优先结果页、按需详细/依据、同卦追问、部分内容保留、安卓可读与旧记录兼容。

第一版可暂缓：新的分享模板、统计可视化、更多音效、完整六爻新引擎、咖啡馆商业功能。暂缓内容不能重新占用首页或强制进入主流程。

交付时附：

1. 本地可运行候选版与明确版本号。
2. 起卦、塔罗、二合一各一套手机/桌面流程截图。
3. 同一输入的新旧结果对照和短解样例。
4. 数字起卦、射覆、断流、重试、追问与缓存更新的验收记录。
5. 可复核的请求数与性能测量，注明样本条件。
6. 旧数据兼容情况、尚未解决的问题、上线与回退步骤。

优先顺序：先缩短结果与修复内容消失，再简化入口，接着完成详细阅读和移动端收尾。
